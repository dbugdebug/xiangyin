# 乡音心伴｜整体架构与团队开发文档

本文按本仓库现有代码整理，供前端、后端、算法同学分工协作。数据库表和已经部署的业务 API 路径保持不变。

## 项目主线

老人使用方言语音与乡音交流；系统把陪伴对话、心理量表筛查和家属/村协管员关怀跟进串成服务链。AI 可辅助转写、理解和表达，但不做心理诊断、不替老人作答；风险信号进入真人复核。

## 当前实际架构

React/TypeScript/Vite 前端部署到 Cloudflare Pages，通过 Supabase Auth 获得会话，并调用 Supabase Edge Function（Deno，位于 supabase/functions/api/index.ts）。Edge Function 验证 Supabase JWT、读取 profiles 角色映射、校验资源权限后访问 Supabase PostgreSQL，并可调用模型服务。

仓库还保留 deploy/ 下的 Flask + Cloudflare Python Workers + Hyperdrive 后端实现。它是另一套可选部署，不与 Supabase Edge Function 的认证令牌混用。发布前要确认 Pages 环境变量指向哪一套 API；现有页面路径仍为 /api/...。

| 层 | 当前实现 | 责任 |
|---|---|---|
| 前端 | React、TypeScript、Vite、React Router、Tailwind | 三角色页面、语音交互、量表体验、会话状态 |
| 身份 | Supabase Auth；比赛期 Edge Function 模拟验证码 | 登录、会话刷新、用户身份 |
| 当前业务 API | Supabase Edge Function + Deno + supabase-js | JWT 校验、角色/资源授权、业务数据、算法编排 |
| 数据 | Supabase PostgreSQL | 现有 elders、profiles、family_relations、emotion_records、activities、alerts、care_messages、referrals |
| 备选后端 | deploy/app.py + Cloudflare Workers + Hyperdrive | 与既有 API 路径兼容的另一种部署实现 |
| 算法 | Edge Function 规则和模型调用，后续 provider adapter | 方言 ASR、陪伴回复、TTS、量表计分、风险辅助 |

## 前端、后端、算法分工

### 前端同学

- 页面在 frontend/src/pages，组件在 frontend/src/components。
- API client 在 frontend/src/lib/api.ts，认证会话在 supabaseAuth.ts，路由角色在 session.ts。
- 负责适老化 UI、语音采集/播放、逐题量表交互、请求状态、角色切换入口和 Pages 构建。
- 本地 xy_role 只控制界面路由，不是服务端授权凭据。

### 后端同学

- 当前前端业务 API 位于 supabase/functions/api/index.ts。
- 负责兼容 /api/...、校验 Supabase JWT、读取 profiles 角色、验证老人/家属资源归属、数据读写和模型调用。
- deploy/ 是备选 Flask Worker，不要将它的演示 token 与 Supabase Auth JWT 混用。
- 数据库迁移须评审。本次角色切换只用现有 Auth 用户、profiles、elders、family_relations，不增加表。

### 算法同学

- 负责目标方言 ASR 评估、方言文本处理、陪伴回复策略、TTS、确定性量表计分和风险辅助。
- 经后端 adapter 接入，不直接写数据库、不信任客户端身份。
- 量表版本、题目、阈值和解释由心理/临床指导人员审核。LLM 不判题、不算分、不诊断。
- 提供模型/提示词版本、方言评测、延迟成本、失败策略和安全边界。

## 当前认证与 API

- 前端 API 根地址由 VITE_SUPABASE_URL + /functions/v1/api 组成；api.ts 使用既有 /api/... 请求路径。
- 演示登录为 POST /api/auth/demo，任意非空验证码，仅作演示。
- 当前用户为 GET /api/me，携带 Supabase Authorization Bearer access token。
- 本次新增演示切换为 POST /api/auth/demo/switch-role，使用当前有效 Supabase 会话，返回固定演示角色的新 Supabase 会话。
- 原有 /api/chat、/api/elders、/api/alerts、/api/care-messages、/api/family/... 等保持兼容。

## 关键数据流

### 方言陪伴

前端录音或识别 → 老人确认文本 → 通过既有聊天 API 提交 → Edge Function 校验会话和老人角色 → 模型回复或安全 mock → 保存必要记录 → 前端显示文字并可语音朗读。低置信度先确认，默认不长期保存原始录音。

### 量表筛查

前端逐题呈现专业人员审核的固定版本 → 用户确认答案 → 后端校验题目和选项 → 确定性规则计分 → 返回筛查提示和后续建议。现有 schema 没有量表会话、逐题答案、结果版本专表；需要持久化历史时先评审新增迁移，不复用情绪或病史字段。

### 风险关怀

规则/模型提供候选信号 → 服务端做权限和风险规则校验 → 写入现有 alerts → 家属/村协查看 → 真人处置、留言或转介。AI 输出仅为需关注提示，不是诊断。

## 演示安全开关

在线角色切换同时受 Pages 构建变量 VITE_DEMO_ROLE_SWITCH_ENABLED 和 Supabase Function secret DEMO_ROLE_SWITCH_ENABLED 控制；正式环境保持关闭。Edge Function 验证当前 JWT 后才签发固定演示身份，不允许客户端传任意用户 ID 或改真实账号角色。

固定演示号码支持 DEMO_ELDER_PHONE、DEMO_FAMILY_PHONE、DEMO_VILLAGER_PHONE 覆盖。默认号码见后端开发说明；如与现有用户冲突，配置独立号码。

浏览器只使用 Supabase publishable/anon key；service role、FAKE_OTP_SECRET、模型 key 仅放服务端 secrets。禁止提交真实手机号、录音、答案和 token。

## 开发阶段和验收

1. 比赛闭环：三端、语音陪伴、量表体验和已有预警闭环可演示；在线切换角色后服务端会话也切换。
2. 算法验证：按目标方言评估 CER、风险短语召回、低置信度确认率和延迟；计分与人工样例一致。
3. 后续产品化：真实 OTP、量表历史迁移、权限审计、实时通知及音频删除策略。

模型失败时回退安全短回复；ASR 失败时允许文字输入；高风险提示真人跟进。量表筛查不等于临床诊断。
